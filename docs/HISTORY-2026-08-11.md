### 3-1. 왜 '빼보기'를 뺐나 — 무엇으로 대체하나

'빼보기(patch-kill)'는 **기능을 일부러 빼서 그 테스트가 실패하는지 보는 것**이다. 테스트가 속 빈 껍데기가 아님을 증명하는 강력한 방법이지만, '넣기 전 버전'을 매번 꺼내 돌려야 하고 서버가 필요한 건 **기능 뺀 이미지를 따로 빌드**해야 해서 비용이 크다.

→ 대신 **직전 버전의 테스트 기록을 확인**한다 (`previous-run-test-review.yaml`). 새 기능이 생겨 테스트가 추가되는 경우가 아니라면, 이번에 새로 증명하지 않고 직전 기록으로 판단한다.

1. 직전 버전에서 **정의된 테스트가 하나도 빠짐없이 실제로 수행됐는지** — 정의만 해두고 안 돌린 것은 실패로 본다
2. **결국 해결했더라도, 오류가 났던 항목은 원인을 함께 기록**한다
3. 그 원인을 **이번 버전의 확인 항목으로 승격**해 같은 오류가 재발하지 않게 한다

그리고 이 확인도 **결과를 남긴다** (`previous-run-test-review-evidence.yaml`) — 소스 검사 결과 기록이 필수인 것과 같은 이유로, 빼보기 대신 넣은 것이니 근거도 남아야 한다.

### 3-2. 보류 2종 — 다음에 결정할 것

- **`upgrade-rehearsal-matrix.yaml` (버전 올림 예행연습 표)** — 용도는 "**진짜 브랜치는 건드리지 않고 일회용 복사본에서 버전 올림을 미리 돌려, 이번 업그레이드가 위험한지 먼저 알아보는 것**". 어떤 버전 조합을 어떤 단계(공식 diff → 우리 코드 diff → 재적용 감지 → 게이트 실행 → 결과 라벨)로 리허설할지 정의해둔다. 4페이지의 1.13.0→1.13.1이 여기 적힌 예행연습이다. 쓸모는 있어 보이나 운영 방식을 더 고민한 뒤 결정.
- **`ui-typecheck-baseline-evidence.yaml` (화면 타입오류 기준선)** — 화면 코드 타입 오류의 기준선을 잡아 **다음 검사 때 새로 늘어난 오류만** 잡아내는 용도. 실제로 얼마나 도움이 되는지 확인 필요.
