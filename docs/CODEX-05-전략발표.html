S02 / 16 · 왜 시작했나

배경과 처음의 생각

목표

우리가 손댄 부분(DB 커넥터·자체 화면·한글 입력 등)이 공식 버전업 뒤에도 안 깨지고 살아 있는지 확인한다.

전제

AI를 쓰는 것 자체는 옳다. 다만 행내에서 운영하는 서비스라 최대한 보수적으로 가야 한다고 봤다.→ 그래서 AI 개입을 최소화하고, 사람·AI 주관을 뺀 채 정해진 규칙(파일 위치·커밋 이력)만 보는 자동 검사로 전부 걸러내는 전략을 먼저 검토했다.

효과

같은 코드면 항상 같은 결과가 나오는 ‘재현 가능한 자동 판정’.

S03 / 16 · 어떻게 만들었나 (초기)

처음 만든 것 — 규칙 기반 자동 검사기

파일 위치‘이 기능은 이 파일들에’를 목록에 적고 대조
커밋 이력커밋마다 꼬리표 + 선언 범위 밖 변경 확인
안전장치애매하면 통과 아닌 ‘막음’(fail-closed)
못박기검사한 코드를 특정 커밋·tree에 고정
예시 — BANK-OM-001 (InstanceCode) 하나가 만드는 관리 문서 2종 + 검사 기준 (실제 값)
① manifests/BANK-OM-001.yaml ← 경로 목록 = ‘경로 기반’의 실체
customization_id: BANK-OM-001   # InstanceCode
allowed_changed_paths:          # 건드려도 되는 경로 ~50개
  - …/resources/instancecode/InstanceCodeResource.java
  - …/json/schema/entity/data/instanceCode.json
  - …/components/InstanceCode/InstanceCodeListPage.tsx
  - …/locale/languages/*.json   (로케일 17개) …
required_changed_paths:         # 반드시 바뀌어야 통과 = 핵심 앵커
  - InstanceCodeResource.java
  - instanceCode.json
② contracts.yaml ← 지켜야 할 ‘불변식’ + 그걸 지키는 테스트
- id: CONTRACT-INSTANCE-CODE
  invariant: codeGroup/codeValue가 CRUD·재색인
             뒤에도 동일하게 조회된다
  required_tests:
    - test_instance_code.py::test_crud_search_roundtrip
  customization_ids: [BANK-OM-001, …]
검사기는 이 둘을 기준으로 검사한다
  1. 경로 기반 — required 경로가 공식과 달라졌나? 없거나 공식과 똑같으면(커스텀 소실) BLOCK.
  2. 커밋 이력 — 커밋에 Customization-ID: BANK-OM-001 꼬리표 + 선언 범위 밖 변경 확인.
  3. 전용 Contract — 그 불변식을 지키는 test_crud_search_roundtrip을 실제 실행 (속 빈 테스트면 patch-kill로 걸러냄).
  4. 못박기 — 검사한 소스 전체의 tree 지문을 lock에 고정 → 바뀌면 감지.
BANK-OM-006(Sybase)는 공유 파일(DatabaseServiceUtils.tsx 등)까지 목록에 + upgrade_watch로 공식 공용 파일(serviceConnection.json) 변경까지 감시.

↑ 여기 보인 건 2종일 뿐 — 이 외에 registry(등록대장)·shared-path-owners(공유파일 소유)·sensitive-zones·repository-layout·debt-thresholds(정책 3종)·patch-kill·runtime·upgrade-rehearsal(계획)·candidate-lock+approval(못박기·승인)·evidence(증거 3종) 등, 커스텀 11개 기준 합쳐 약 25개의 관리 파일이 함께 돈다. (→ 6페이지 ‘운영 부담’의 실체)

S05 / 16 · 왜 ‘룰베이스 검사기’인가

강점 — LLM 혼자선 보장 못 하는 것들

아래는 전부 LLM에게 맡기면 “됐다”는 말로 끝나는 것 — 그래서 결정론적 검사기가 필요하다.

patch-kill

커스텀이 없으면 그 테스트가 반드시 실패해야 진짜로 인정(‘속 빈 테스트’ 색출). 예) Sybase — Sybase 코드가 없던 이전 커밋을 꺼내 그 테스트를 돌리니 실패 → “이 테스트가 진짜 Sybase를 지킨다”가 입증됨(그때도 통과했다면 = 속 빈 테스트). ※ 이 테스트는 소스 파일만 열어보는 파이썬 테스트라 빌드·서버 없이 실행됨. 반면 InstanceCode처럼 실제 서버로 봐야 하는 건 기능 뺀 이미지가 따로 필요(일부 pending — 12p).

막고 보기(fail-closed)

기능별 검사(테스트) 하나라도 못 돌면 ‘통과’가 아니라 ‘막음’으로 떨어진다. 검사할 데이터가 없거나 오류·시간초과로 검사를 못 돌린 경우, 검사기는 그걸 통과로 세지 않는다. 예: ‘확장컬럼 화면’을 볼 데이터가 인스턴스에 없어 그 검사를 건너뛰면(skip) → 통과가 아니라 막음(BLOCK). LLM이라면 “대충 됐다”로 넘어갈 지점을 원천 차단.

candidate-lock(못박기)

검사한 코드를 특정 커밋·tree에 고정, 이후 변경을 감지. LLM 기록은 나중에 고쳐도 티가 안 남 → 검사기는 지문이 어긋나면 드러남(전자서명은 아님, 변경 ‘감지’).

data-check(기계 대조)

화면·API 값을 행 단위로 기계 비교. LLM/사람 눈대중은 “비슷하니 맞겠지” → 검사기는 정확히 일치/불일치로 판정(화면 A matched).

결정론(재현성)

같은 코드면 항상 같은 결과. LLM은 같은 입력에도 답이 흔들림 → 검사기는 재현 가능해 ‘배포 기준’이 될 수 있음.

반복

S07 / 16 · 드러난 한계 ②

규칙 검사만으로는 못 보는 것들

이동(리로케이션)

공식이 코드를 다른 파일로 옮기면 못 따라간다 (가장 큰 약점). 실제: Sybase의 case DatabaseServiceType.Sybase 코드가 DatabaseServiceUtils.tsx → *PureUtils.ts로 이사. 검사기는 매니페스트의 옛 경로만 봐서 “커스텀이 사라졌다”며 실패(BLOCK). 실제론 새 파일에 멀쩡히 살아있었음 = 오판.

의미(반쪽 병합)

검사기의 ‘생존’ 판정 기준은 “커스텀 파일이 공식과 다른가”다. 그런데 “다르다” ≠ “기능이 온전하다”. 병합이 어긋나 커스텀 로직이 반쪽만 들어가도 ‘공식과 다름’은 성립 → survived(통과)로 봐버림. (또 DB 마이그레이션이 어긋나 서버가 아예 안 뜬 적도 있음 — 파일은 멀쩡한데 런타임이 깨진 경우. 경로만 보는 검사론 못 잡음.)

입력(사람 값)

일부 판단 근거를 사람이 손으로 적는다. 실제: 충돌률·승인자 같은 값은 사람이 입력 → 검사기는 그 숫자가 ‘진짜인지’는 확인 못 함(형식만 검사).

결론규칙(파일·글자 기준)을 더 붙여도 이 약점은 반복된다 — 구조적 한계다. 단, 이건 변화가 클 때 얘기다 — 작은 버전업에선 규칙 기반이 잘 통했다.
S08 / 16 · 참고한 다른 접근

8/5 공유된 ‘LLM 기반 운영 방식’ (참고)

개념

규칙·지식 문서·자동화로 LLM이 버전 포팅을 빠르게 수행하는 방식. “포팅 시간 크게 단축(빠르고 체계적)”은 그 방식의 자체 보고 수치 — 우리가 실행·검증한 건 아니다.

구조

변경·수정·테스트·결과 기록을 대부분 LLM이 스스로 수행하고, 그 결과도 스스로 문서에 적는다.

우리 생각 — 검증이 아니라 방향 제안이 접근에 검사기로 ‘각 판단의 근거를 자동으로 뒷받침’하는 층을 더하면, 속도(LLM)는 살리고 신뢰(근거)는 끌어올릴 수 있겠다. 경쟁이 아니라 ‘빠른 실행 + 단단한 근거’로 합쳐진다.
S09 / 16 · 방향 전환

LLM이 일하고, 검사기가 근거를 붙인다

LLM

판단·제안무엇을 바꿀지, 코드가 어디로 옮겨졌을지, 충돌 해결, 필요한 테스트.

검사기

뒷받침그 판단을 실제 코드·실행 증거로 확인하고, 위험하면 막는다.

핵심 규칙LLM이 ‘됐다(✅)’고 적어도, 실제 코드·실행 증거가 없으면 ‘미확인’으로 표시한다. 증거 없다고 곧장 ‘거짓’으로 몰지 않는다 → 확인 반박 미확인 사람검토 4단계.
S10 / 16 · 도입 제안 — 검사기 시스템

커스텀 하나(BANK-OM ID)가 검증되는 과정

제안: 하이브리드에서 LLM 작업의 ‘증거 층’으로 이 검사기를 도입한다 (자랑이 아니라 도입 대상). 커스텀 하나가 아래 6단계로 등록·검사·증거화된다.

1

등록 — Manifest · Registry · Contract

무엇을·어디를 바꿨고, 어떤 전용 계약으로 지킬지 선언한다.

2

커밋 · 변경범위 검사

이 ID가 선언한 범위만 건드렸는지, 공식 계보 위에 얹혔는지 확인.

3

공용 파일의 ID별 코드 검사

여러 기능이 공유하는 파일에서 이 ID 몫의 코드가 살아있고 공식과 달라졌는지.

4

전용 검사 실행

이 기능만의 검사(API/화면/소스). 속 빈 테스트면 patch-kill로 걸러낸다.

5

commit · 이미지와 결과 결속

검사 결과를 특정 커밋·이미지에 못박아 바꿔치기·사후수정을 감지.

6

승인 · 증거 보관

권한자 승인 + 증거(무엇을·어떤 코드에서·어떤 결과) 보관. 승인은 결과에 결속.

6페이지 한계와의 연결“관리 파일이 많다”(6p)는 부담을 그대로 두지 않는다 — 이 산출물(manifest·contract 등)을 사람이 아니라 LLM이 생성·갱신하고, 검사기는 검증만 한다. 즉 파일 관리 부담은 LLM으로 옮기고, 검사기는 예측 가능한 판정자로 남는다.

어떻게 쓰나 — 검사기가 자동으로 남긴다. ‘직전에 무엇이 돌았고 무엇이 왜 실패했으며, 그 원인을 이번에 어떻게 막았는지’가 한 파일에 남아 다음 버전 올림의 근거가 된다.
채택 방침A·C = LLM이 초안 생성(사람 확인) · B·D = 사람·조직이 고정 · E = 검사기 자동 생성. → LLM의 속도는 쓰되, 기록은 자유서술 MD가 아니라 이 구조화 파일로 남겨 검사기가 검증한다.
1차 검토 요약제외한 것은 지우지 않고 삭선으로 남겨 왜 뺐는지까지 보이게 했다. 핵심 변경 두 가지 — ① ‘빼보기’(일부러 기능을 빼서 검사가 실패하는지 보는 것)를 빼고, 대신 직전 버전의 테스트 기록을 확인한다(모두 수행됐나 · 실패했다면 원인은 무엇이었나 → 같은 오류 재발 방지). ② 우리 스스로를 제한하는 정책은 덜어내고, 진짜 위험한 구역 차단만 남긴다.
S14 / 16 · 자유서술 MD가 아니라 관리파일로

‘자유서술 MD 자기보고’가 아니라 ‘관리파일 + 검사기’

8/5 방식은 LLM이 자유서술 MD(KB-CUSTOM-*.md)에 “했다”고 적는 자기보고. 우리는 앞의 구조화 관리파일(S13)을 검사기가 대조한다 — 문서는 안 해보고/고쳐도 티가 안 나지만, 관리파일+검사기는 형식이 정해져 기계가 검증하고 보호된 CI에서 생성·보관하면 변경을 감지한다. 아래는 그 대비의 대표 예시 4개.

S15 / 16 · 오해 방지

지켜야 할 조건 & 검사기의 정확한 위치

독립성

LLM이 실행·기록·증거·승인을 다 하면 ‘독립 검증’이 아니다. 별도의 보호된 자동화(CI)가 실제 코드를 받아 검사를 돌려야 한다 — LLM은 요약만, 판정은 못 바꾼다.

범위

검사기 초록불 = “코드·기록·증거가 앞뒤 맞다”는 뜻이지, “모든 기능 정상·배포해도 안전”까지는 아니다.

배포4

최종 배포엔 4가지: ①변경 범위 정합성 ②검사한 코드=배포할 코드 ③실제 서버 동작 검사 ④권한 있는 사람 승인.
