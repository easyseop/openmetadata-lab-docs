S03 / 17 · 어떻게 만들었나 (초기)

처음 만든 것 — 규칙 기반 자동 검사기

파일 위치‘이 기능은 이 파일들에’를 목록에 적고 대조
커밋 이력커밋마다 꼬리표 + 선언 범위 밖 변경 확인
안전장치애매하면 통과 아닌 ‘막음’(fail-closed)
못박기검사한 코드를 특정 커밋·tree에 고정
예시 — BANK-OM-001 (InstanceCode) 하나가 만드는 관리 문서 2종 + 검사 기준 (실제 값)
① manifests/BANK-OM-001.yaml ← 경로 목록 = ‘경로 기반’의 실체
customization_id: BANK-OM-001   # InstanceCode
allowed_changed_paths:          # 건드려도 되는 경로 ~50개
  - …/resources/instancecode/InstanceCodeResource.java
  - …/json/schema/entity/data/instanceCode.json
  - …/components/InstanceCode/InstanceCodeListPage.tsx
  - …/locale/languages/*.json   (로케일 17개) …
required_changed_paths:         # 반드시 바뀌어야 통과 = 핵심 앵커
  - InstanceCodeResource.java
  - instanceCode.json
② contracts.yaml ← 지켜야 할 ‘불변식’ + 그걸 지키는 테스트
- id: CONTRACT-INSTANCE-CODE
  invariant: codeGroup/codeValue가 CRUD·재색인
             뒤에도 동일하게 조회된다
  required_tests:
    - test_instance_code.py::test_crud_search_roundtrip
  customization_ids: [BANK-OM-001, …]
검사기는 이 둘을 기준으로 검사한다
  1. 경로 기반 — required 경로가 공식과 달라졌나? 없거나 공식과 똑같으면(커스텀 소실) BLOCK.
  2. 커밋 이력 — 커밋에 Customization-ID: BANK-OM-001 꼬리표 + 선언 범위 밖 변경 확인.
  3. 전용 Contract — 그 불변식을 지키는 test_crud_search_roundtrip을 실제 실행 (속 빈 테스트면 patch-kill로 걸러냄).
  4. 못박기 — 검사한 소스 전체의 tree 지문을 lock에 고정 → 바뀌면 감지.
BANK-OM-006(Sybase)는 공유 파일(DatabaseServiceUtils.tsx 등)까지 목록에 + upgrade_watch로 공식 공용 파일(serviceConnection.json) 변경까지 감시.

↑ 여기 보인 건 2종일 뿐 — 이 외에 registry(등록대장)·shared-path-owners(공유파일 소유)·sensitive-zones·repository-layout·debt-thresholds(정책 3종)·patch-kill·runtime·upgrade-rehearsal(계획)·candidate-lock+approval(못박기·승인)·evidence(증거 3종) 등, 커스텀 11개 기준 합쳐 약 25개의 관리 파일이 함께 돈다. (→ 6페이지 ‘운영 부담’의 실체)

▸ 업그레이드 테스트를 하며 겪은 어려움 — 리로케이션은 드러난 계기 중 하나일 뿐이었다.

① 코드 이동

코드가 어디로 옮겨갔는지 규칙으론 못 따라간다. 옛 경로만 보고 “사라졌다”고 오판 — 리로케이션.

② 반쪽 병합

검사기는 우리 코드가 살아있는지를 “그 파일이 공식 버전과 다른가”로만 판정한다 — 다르면 들어간 것으로 본다. 어떻게 다른지는 보지 않는다. 그래서 병합이 어긋나 커스텀이 절반만 들어가도 ‘다르다’는 성립하므로 그대로 통과된다.

③ 등록할 경로가 많다

검사기에게 “우리 커스텀이 여기 있다”고 경로를 전부 등록해야 한다. Sybase 하나에 18개 — 그중 11개가 프로그램이 자동으로 만들어내는 파일이라, 다시 만들어질 때마다 내용이 통째로 바뀐다. 등록해둔 경로가 계속 어긋나고, 기능이 늘수록 곱절로 늘어난다.

④ 관리 부담

그때마다 관리 파일 ~25개와 커밋 이력을 사람이 갱신해야 한다. 고칠수록 따라 붙는 일이 늘어난다.

S05 / 17 · 드러난 한계 ① — 규칙 검사의 사각

규칙 검사만으로는 못 보는 것들

이동(리로케이션)

공식이 코드를 다른 파일로 옮기면 못 따라간다 (가장 큰 약점). 실제: Sybase의 case DatabaseServiceType.Sybase 코드가 DatabaseServiceUtils.tsx → *PureUtils.ts로 이사. 검사기는 매니페스트의 옛 경로만 봐서 “커스텀이 사라졌다”며 실패(BLOCK). 실제론 새 파일에 멀쩡히 살아있었음 = 오판.

의미(반쪽 병합)

검사기의 ‘생존’ 판정 기준은 “커스텀 파일이 공식과 다른가”다. 그런데 “다르다” ≠ “기능이 온전하다”. 병합이 어긋나 커스텀 로직이 반쪽만 들어가도 ‘공식과 다름’은 성립 → survived(통과)로 봐버림. (또 DB 마이그레이션이 어긋나 서버가 아예 안 뜬 적도 있음 — 파일은 멀쩡한데 런타임이 깨진 경우. 경로만 보는 검사론 못 잡음.)

입력(사람 값)

일부 판단 근거를 사람이 손으로 적는다. 실제: 충돌률·승인자 같은 값은 사람이 입력 → 검사기는 그 숫자가 ‘진짜인지’는 확인 못 함(형식만 검사).

결론규칙(파일·글자 기준)을 더 붙여도 이 약점은 반복된다 — 구조적 한계다. 단, 이건 변화가 클 때 얘기다 — 작은 버전업에선 규칙 기반이 잘 통했다.

S07 / 17 · 왜 ‘룰베이스 검사기’인가

강점 — LLM 혼자선 보장 못 하는 것들

아래는 전부 LLM도 할 수 있는 일이다. 차이는 능력이 아니라 누가 증언하느냐에 있다 — LLM이 하면 LLM의 말이 되고, 검사기가 하면 증거가 된다.

허위 테스트 방지

기능이 되는지가 아니라, 그 테스트가 진짜인지를 검사한다.

  1. 커스터마이징 기능 테스트 사전 정의
  2. 공식 버전에서 테스트 — 기대결과 FAIL
  3. 커스텀 버전에서 테스트 — 기대결과 PASS
  4. 2번이 PASS면 → 속 빈 테스트 (3번의 초록불에 근거 없음)
LLM이 하면“공식 버전에서 돌려봤고 실패했습니다” — 그 말이 사실인지 알 방법이 없다.검사기가 하면어느 커밋에서 무슨 테스트가 어떻게 실패했는지 파일로 남는다.

▸ 테스트는 LLM이 만들어도 된다. 사람이 그걸 다 읽어보고 “제대로 짰나”를 판단할 수는 없으니, 커스텀 없이 한 번 돌려 걸러낸다 — LLM에게 테스트를 맡길수록 이 항목이 더 필요해진다.

▸ 한계 — 아무것도 안 보는 테스트는 걸러내지만, 덜 보는 테스트는 못 걸러낸다. 예: status_code == 200만 확인해도 커스텀이 없으면 404라 실패하므로 “진짜 테스트”로 인정된다 — 정작 값이 맞는지·검색에 반영되는지는 안 보는데도. 그래서 사람이 읽어야 할 한 가지가 남는다 → 12페이지의 불변식.

실제 결과물
# source-patch-kill-evidence.yaml
gates:
- name: source-patch-kill:BANK-OM-006        # Sybase
  reasons: ['proven: required test failed without the patch']
  verdict: pass                              # ← 커스텀 없으니 실패 = 이 테스트는 진짜
pending_high_critical_ids: [BANK-OM-001, 002, 003]  # ← 아직 못 한 것도 남는다
막고 보기(fail-closed)

검사 하나라도 못 돌면 ‘통과’가 아니라 ‘막음’이다.

  1. 필수 검사 목록 사전 정의
  2. 실행 — 데이터 없음·오류·시간초과는 ‘건너뜀’으로 기록
  3. 집계 — 실패가 0이어도 건너뜀이 있으면 BLOCK
LLM이 하면같은 상황에서 어떤 때는 막고 어떤 때는 넘어간다.검사기가 하면건너뜀이 하나라도 있으면 항상 BLOCK — 예외 없음.
실제 결과물
# 화면 검사할 데이터가 없어 7개를 못 돌린 경우
runtime contracts:  2 pass · 7 skipped  →  verdict: block
                                            ↑ 실패가 0인데도 통과가 아니다
못박기(candidate-lock)

검사한 코드를 커밋에 고정해, 이후 바뀌면 드러난다.

  1. 검사 직전 코드 지문 기록 (커밋·tree)
  2. 그 코드로 검사 실행 — 결과에 지문 결속
  3. 나중에 대조 — 지문이 다르면 다른 코드
LLM이 하면자기가 쓴 기록을 자기가 고칠 수 있다.검사기가 하면보호된 자동화가 쓰고, 지문이 어긋나면 드러난다.
실제 결과물
# source-candidate-evidence.yaml
candidate:
  commit_sha: 849ae756cd23...   # 검사한 바로 그 코드
  tree_sha:   22f92a8e0fd2...
  candidate_lock_digest: sha256:61a3f02d3f22...   # 내용 바뀌면 어긋남
기계 대조(data-check)

고정된 건 값이 아니라 판정 규칙이다. 값은 매번 달라져도, “무엇을 맞다고 볼 것인가”는 늘 같다.

  1. 값이 정해진 것 → 그 값과 그대로 대조 (예: 스키마 제목이 SybaseConnection인가)
  2. 값이 매번 달라지는 것 → 관계로 대조 — 넣고 → 꺼내고 → 고치고 → 검색까지 넣은 값이 그대로 나오는지
  3. 끝나면 흔적을 지운다 (다음 실행에 영향 없게)
LLM이 하면값이 많아지면 “대체로 맞다”로 흐른다.검사기가 하면넣은 값과 나온 값을 한 건씩 대조 — 하나만 달라도 실패.
실제 테스트 코드
# test_instance_code.py :: test_crud_search_roundtrip
suffix  = uuid.uuid4().hex[:12]                      # 매번 새 값을 만든다
payload = {"codeGroup": "CONTRACT", "codeValue": suffix, "codeName": "before"}

created = client.post("/v1/instanceCodes", payload)  # 넣고
fetched = client.get(f"/v1/instanceCodes/{id}")
assert fetched["codeValue"] == payload["codeValue"]  # 넣은 값 == 나온 값

updated = client.put(..., dict(payload, codeName="after"))
assert updated["codeName"] == "after"                # 고친 값이 반영되나

hit = wait_for(search_hit)                           # 검색 색인에도
assert hit["_source"]["codeValue"] == payload["codeValue"]
finally: client.delete(...)                          # 흔적 지움
결정론(재현성)

이 항목만은 LLM이 구조적으로 못 한다. 같은 코드면 항상 같은 결과가 나와야 배포 기준이 될 수 있다.

  1. 같은 코드 지문이면
  2. 같은 검사 절차로
  3. 항상 같은 판정 — 어제 통과한 게 오늘 막히지 않는다
LLM은같은 입력에도 답이 흔들린다 — 그래서 “배포해도 되나”의 기준으로 삼을 수 없다.검사기는규칙이라 흔들리지 않는다 — 이건 흉내로 메울 수 없는 차이다.

8/5 공유된 ‘LLM 기반 운영 방식’ (참고)

개념

규칙·지식 문서·자동화로 LLM이 버전 포팅을 빠르게 수행하는 방식. “포팅 시간 크게 단축(빠르고 체계적)”은 그 방식의 자체 보고 수치 — 우리가 실행·검증한 건 아니다.

구조

변경·수정·테스트·결과 기록을 대부분 LLM이 스스로 수행하고, 그 결과도 스스로 문서에 적는다.

우리 생각 — 검증이 아니라 방향 제안이 접근에 검사기로 ‘각 판단의 근거를 자동으로 뒷받침’하는 층을 더하면, 속도(LLM)는 살리고 신뢰(근거)는 끌어올릴 수 있겠다. 경쟁이 아니라 ‘빠른 실행 + 단단한 근거’로 합쳐진다.
S10 / 17 · 방향 전환

LLM이 일하고, 검사기가 근거를 붙인다

LLM

판단·제안무엇을 바꿀지, 코드가 어디로 옮겨졌을지, 충돌 해결, 필요한 테스트.

검사기

뒷받침그 판단을 실제 코드·실행 증거로 확인하고, 위험하면 막는다.

▸ 구체적으로 — LLM의 주장을 검사기가 이렇게 확인한다

“이 파일 바꿨다”

실제 커밋의 변경 내역을 직접 대조한다.

“충돌 0건”

임시로 실제 병합해 충돌 수를 센다. 안 해보고 적어도 티가 안 나는 주장이라, 세어보는 것 말고는 확인할 방법이 없다.

“테스트 통과”

실제 서버에서 다시 실행한다. 미실행은 통과가 아니다.

“승인함”

승인을 결과에 묶어 입력이 바뀌면 자동으로 무효가 되게 한다.

핵심 규칙LLM이 ‘됐다(✅)’고 적어도, 실제 코드·실행 증거가 없으면 ‘미확인’으로 표시한다. 증거 없다고 곧장 ‘거짓’으로 몰지 않는다 → 확인 반박 미확인 사람검토 4단계.
S11 / 17 · 도입 제안 ① — 검증되는 과정

커스텀 하나(BANK-OM ID)가 검증되는 과정

제안: 하이브리드에서 LLM 작업의 ‘증거 층’으로 이 검사기를 도입한다 (자랑이 아니라 도입 대상). 커스텀 하나가 아래 6단계로 등록·검사·증거화된다.

1

등록 — Manifest · Registry · Contract

무엇을·어디를 바꿨고, 어떤 전용 계약으로 지킬지 선언한다.

2

커밋 · 변경범위 검사

이 ID가 선언한 범위만 건드렸는지, 공식 계보 위에 얹혔는지 확인.

3

공용 파일의 ID별 코드 검사

여러 기능이 공유하는 파일에서 이 ID 몫의 코드가 살아있고 공식과 달라졌는지.

4

전용 검사 실행

이 기능만의 검사(API/화면/소스). 속 빈 테스트면 patch-kill로 걸러낸다.

5

commit · 이미지와 결과 결속

검사 결과를 특정 커밋·이미지에 못박아 바꿔치기·사후수정을 감지.

6

승인 · 증거 보관

권한자 승인 + 증거(무엇을·어떤 코드에서·어떤 결과) 보관. 승인은 결과에 결속.

6페이지 한계와의 연결“관리 파일이 많다”(6p)는 부담을 그대로 두지 않는다 — 이 산출물(manifest·contract 등)을 사람이 아니라 LLM이 생성·갱신하고, 검사기는 검증만 한다. 즉 파일 관리 부담은 LLM으로 옮기고, 검사기는 예측 가능한 판정자로 남는다.
S12 / 17 · 도입 제안 ② — LLM이 만든다

LLM이 만들고, 사람이 확인한다 관리 파일 9종

6페이지에서 말한 “관리할 파일이 너무 많다”는 부담의 정체가 바로 이 9종이다. 없애는 게 아니라 작성·갱신을 LLM에게 넘긴다 — 사람은 확인만, 검사기는 판정만 한다.

▸ 1차 검토 (이 장부터 3장에 걸친 전체 18종 기준) — 채택 8 · 제외 3(삭선·흐림, 지우지 않고 남김) · 보류 5 · 신규 2 제안  ·  각 카드를 펼치면 용도 · 실제 예시 · 검사기 사용법 · LLM 체제에서의 역할이 나옵니다.

먼저 — 4페이지와 모순 아닌가?“경로 기반이 어렵다·관리가 번거롭다”고 해놓고 경로·목록 파일을 다 남기는 것으로 보일 수 있다. 구분이 필요하다.
버린다

경로가 안 맞으면 “죽었다”고 판정하던 것. Sybase에서 실제로 오판한 지점.

남긴다

경로를 “어디서부터 찾을지”의 출발점으로 쓰는 것. 불일치 = 실패가 아니라 ‘확인 필요’ → LLM이 새 위치를 찾는다.

즉 경로 목록이 없으면 LLM도 일을 못 한다 — “이 코드가 어디로 갔는지 찾아봐”라고 시키려면 원래 어디 있었는지를 알려줘야 한다. 이 목록은 리로케이션 대응의 장애물이 아니라 입력이다. 버리면 무엇이 우리 커스텀인지조차 모르게 된다. 마찬가지로 부담의 정체는 ‘파일이 있다’가 아니라 ‘사람이 갱신한다’였다 → 갱신을 LLM에게 넘긴다.

A. 정의 — 무엇이 커스텀인가LLM이 초안, 사람이 확인1차 검토 → 5종 전부 채택 (단, 경로는 ‘판정 기준’이 아니라 ‘출발점’으로 강등)

검사기의 정확한 위치 — LLM 위에 얹는 안전장치

검사기는 LLM을 대신하지 않는다. 검사도 판단도 LLM이 먼저 한다 — 검사기는 그 결과를 한 번 더 확인할 뿐이다. 그것도 LLM이 스스로 확인할 수 없는 것만 본다.

1차 — LLM

무엇을 바꿀지 정하고, 옮겨간 코드를 찾고, 충돌을 풀고, 검사까지 직접 돌린다. 속도는 전부 여기서 나온다. 검사기가 이 자리를 뺏지 않는다.

2차 — 검사기

같은 일을 다시 하지 않는다. LLM이 자기 자신에 대해 답할 수 없는 것만 확인한다 — ① 정말 돌렸는가 ② 검사한 코드가 배포할 코드와 같은가 ③ 그 결과가 나중에 바뀌지 않았는가.

그래서 독립성

LLM이 실행·기록·증거·승인을 다 하면 ‘한 번 더’가 성립하지 않는다. 별도의 보호된 자동화(CI)가 실제 코드를 받아 검사를 돌려야 한다 — LLM은 요약만, 판정은 못 바꾼다.

한 줄검사기를 ‘LLM보다 똑똑한 판정자’로 쓰면 실패한다 — 그건 이미 해봤다. ‘LLM이 한 일을 한 번 더 확인하는 안전장치’로 쓰면 부담은 작고 얻는 건 크다.
